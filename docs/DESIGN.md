# specops — Design Principles (แนวทางสำหรับผู้พัฒนา)

> อ่านก่อน `SPECOPS-BRIEF.md` · BRIEF บอกว่า**ทำอะไร** ไฟล์นี้บอกว่า**ทำไม** และ**ตัดสินใจอย่างไรเมื่อสเปกไม่ครอบคลุม**
> specops ออกแบบใหม่ทั้งหมด ไม่สืบทอดโค้ด สเปก หรือกฎจากที่ใด · ถ้าพบตัวเองกำลัง "รักษาความเข้ากันได้" กับสิ่งที่ไม่ได้อยู่ใน repo นี้ ให้หยุด

---

## 1. เจตนา

specops มีไว้ตอบคำถามเดียวให้ได้จาก**ข้อมูล** ไม่ใช่จากความจำหรือการอนุมาน:

> **"requirement ข้อนี้ — ลูกค้าขออะไร · ออกแบบไว้ยังไง · ลูกค้าเซ็นอะไร · โค้ดไหนสร้าง · เทสต์ไหนพิสูจน์ · ผลล่าสุดคืออะไร · ถ้าเปลี่ยน กระทบอะไร"**

ผู้ใช้คือ consultant คนเดียวที่ทำครบสายและต้องวางงานได้เป็นเดือนแล้วกลับมาทำต่อ ดังนั้นทุกอย่างต้องอยู่บนดิสก์ในรูปที่ script อ่านได้ และคนอ่านออก

**Analogy กองถ่ายหนัง** (ใช้เมื่ออธิบายอะไรก็ตามให้ผู้ใช้):

| กองถ่าย | specops | ความหมาย |
|---|---|---|
| เจตนานายทุน | REQ | ลูกค้าอยากได้อะไร |
| โลกของเรื่องและกฎของโลก | ENT / BR | สิ่งที่มีอยู่และสิ่งที่ห้ามละเมิด |
| บทฉาก | UC | ใครทำอะไรตามลำดับ ผิดพลาดแล้วยังไง |
| storyboard | UI / MCK | ภาพที่ลูกค้าเซ็นก่อนถ่าย |
| shot list | SCN / TC | สิ่งที่ต้องถ่ายให้ได้เพื่อพิสูจน์ว่าฉากใช้ได้ |
| revision pages ของบท | CR | การแก้บทกลางกองที่ทุกแผนกต้องรู้ |
| script supervisor | `change:impact` + gates | คนตรวจ continuity ว่าทุกฉากยังตรงบทล่าสุด |
| callsheet | `core:next` | ใบบอกว่าวันนี้ทำอะไร |

## 2. หลักการออกแบบ 8 ข้อ

### P1 — กฎอยู่ใน state ไม่ใช่ใน prompt
**หลัก:** พฤติกรรมของระบบถูกกำหนดโดยสถานะของ artifact และ edge ในกราฟ script อ่านสถานะแล้วอนุญาต/ปฏิเสธ · prompt มีหน้าที่แค่เรียก script และแสดงผล
**เหตุผล:** กฎในร้อยแก้วทบกันทุกครั้งที่เพิ่ม plugin จนไม่มีใครรู้ว่ากฎไหนยังใช้ · กฎใน script มีที่เดียว ทดสอบได้ และพังดังเมื่อผิด
**ในโค้ด:** ทุกข้อจำกัดเป็น function ใน `checks.mjs` · คำสั่ง `.md` ยาวไม่เกิน 40 บรรทัดและไม่มีคำว่า "ต้อง…ก่อน"
**ถูก:** `dev:task` ปฏิเสธเพราะ `isFrozen(UI-rental-003)` คืน true · **ผิด:** `task.md` เขียนว่า "ตรวจก่อนว่าไม่มี CR ค้าง"

### P2 — Rule คือหน่วยวัด
**หลัก:** BR ไม่ใช่ scenario คือสิ่งที่ต้องนับว่าครอบคลุมครบไหม · BR เกาะที่ *step* ของ UC (`enforces`) ไม่ใช่ที่ระดับ capability
**เหตุผล:** กฎที่ไม่มี step ไหนบังคับคือกฎที่จะไม่ fire ตอนส่งมอบ — พบเสมอเมื่อกฎเกาะไว้ระดับสูงเกินไป · scenario เป็นสิ่งที่ *พิสูจน์* กฎ ไม่ใช่ตัวกฎ
**ในโค้ด:** gate "ทุก BR ถูก enforce โดย ≥1 step" เป็น error ไม่ใช่ warn · BR/CALC มีเวอร์ชันใน id · เปลี่ยน = เวอร์ชันใหม่ เก่า retired
**ถูก:** `UC.main[1].enforces = ["BR-rental-006@v1"]` · **ผิด:** `UC.rules = [...]` ที่ระดับบน หรือ copy ข้อความกฎมาใส่ใน UC

### P3 — Traceability คือสินค้า ไม่ใช่ผลพลอยได้
**หลัก:** ทุก artifact มี id จากตารางเดียว ทุก id ที่ปรากฏใน record เป็น edge · edge ที่มีชื่อเขียนโดยเจ้าของ `from` เท่านั้น · AI อ่านกราฟผ่าน slice ไม่ใช่เปิดไฟล์
**เหตุผล:** ถ้า trace ต้องเติมทีหลัง มันจะไม่ถูกเติม · ถ้ากราฟจบที่ design การเปลี่ยนแปลงไปไม่ถึงโค้ดและเทสต์
**ในโค้ด:** id ก่อนเนื้อหาเสมอ · `core:query` คือทางเดียวที่คำสั่งอื่นอ่าน artifact · trace edge ไม่ชี้ข้ามชั้น (TSK ชี้ UC/AC ไม่ชี้ BR ตรง — ให้ UC พาไป)
**ถูก:** `query UI-rental-003` แล้วอ่านผล · **ผิด:** `cat design/rental/screens.json` เพื่อ "ดูภาพรวม"

### P4 — หน้าจอมาจาก 3 แหล่ง ไม่ใช่แหล่งเดียว
**หลัก:** UI เกิดจาก G1 use case (สิ่งที่ลูกค้าขอ) + G2 master (จาก `ENT.kind`) + G3 baseline ต่อ app type (สิ่งที่ทุกระบบต้องมี) + G4 cross-cutting (จาก NFR)
**เหตุผล:** ลูกค้าไม่เคยขอหน้า login หรือหน้ากำหนดสิทธิ์ เพราะถือว่ามีอยู่แล้ว — generator ที่อ่านแค่ requirement จึงไม่มีทางได้หน้าเหล่านั้น · ตู้ไฟไม่ได้มาจาก wish list แต่มาจากกฎหมายอาคาร
**ในโค้ด:** `ENT.kind` บังคับ · `project.json.apps[].type/owns/auth` ขับ G2/G3 · UI มี `origin` เพื่อแยกตอนประเมินราคา · coverage gates 4 ข้อ
**ถูก:** ประกาศ app ใหม่แล้ว login/profile โผล่เอง · **ผิด:** ผู้ใช้ต้องพิมพ์ "อย่าลืมหน้า login"

### P5 — การเปลี่ยนแปลงเป็น artifact · impact ตัดสิน lane ไม่ใช่คำพูดลูกค้า
**หลัก:** ทุกคำขอเข้า CR · script เดินกราฟหาสิ่งที่กระทบ · discriminator เดียว: "ผู้ใช้จะเห็นหรือทำอะไรที่ไม่มี artifact ประกาศไหม" → ไม่ = lane `ui` · ใช่ = lane `full`
**เหตุผล:** "ไม่ได้เปลี่ยนโลจิก" เป็นคำที่ลูกค้าพูดเสมอและผิดบ่อย โดยเฉพาะรายงาน · ทางลัดที่ไม่ผ่าน CR ทำให้ baseline ไม่ตรงของจริงและเสียหลักฐานคิดเงิน
**ในโค้ด:** ไม่มีคำสั่งใดแก้ artifact ที่ approved แล้วโดยไม่มี CR · `apply` เปิดสถานะแต่ไม่แก้เนื้อหา · finding ที่ root cause อยู่ที่สเปกเปิด CR เอง
**ถูก:** CR display → impact พบแค่ UI 1 หน้า → lane ui · **ผิด:** แก้ `screens.json` ตรง ๆ เพราะ "แค่เพิ่มฟิลด์"

### P6 — ความจริงมาจากการรัน ไม่ใช่การประกาศ
**หลัก:** เสร็จ = คำสั่งที่รันจริงและผลที่ได้ (`proof[]`) · ตัวเลขที่ถูกต้อง = golden dataset ที่คนเซ็น · gate ที่ไม่มี script = LIMIT ที่พิมพ์ทุกครั้ง
**เหตุผล:** LLM ประกาศว่าเสร็จได้ทุกเมื่อ · คำตัดสินของ LLM คือความเห็น · การ "ผ่านเงียบ" อันตรายกว่าการแดง
**ในโค้ด:** TSK ปิดไม่ได้ถ้า `proof[]` ว่าง · unit test expected = GD คำต่อคำ · gates.mjs พิมพ์ LIMIT ไม่ข้าม
**ถูก:** `proof: [{cmd:"dotnet test …", result:"12 passed", at:…}]` · **ผิด:** `status: "done"` พร้อมคำอธิบายว่าทดสอบแล้ว

### P7 — ไฟล์เล็ก หนึ่งเจ้าของ อ้างด้วย id
**หลัก:** ไฟล์ที่ AI อ่าน ≤300 บรรทัด · แตกตาม module/aggregate/app · plugin เขียนได้เฉพาะโฟลเดอร์ตัวเอง · registry เป็น cache
**เหตุผล:** ไฟล์เดียวโตถึงหลายพันบรรทัดภายในโปรเจกต์เดียว แล้ว token หมดไปกับการอ่านสิ่งที่ไม่เกี่ยว · การ regenerate เขียนทับทั้งไฟล์ ถ้าสอง plugin แชร์ไฟล์ ข้อมูลอีกฝ่ายหายเงียบ
**ในโค้ด:** G-core-005 (บรรทัด) · G-core-002/007 (เจ้าของ) · export/ ไม่ถูกอ่านกลับ · ผลลัพธ์ที่ต้องมาจากสองฝ่ายแยกเป็นสองไฟล์เชื่อมด้วย id
**ถูก:** `design/rental/screens.json` + `trace.mock.json` · **ผิด:** mock เขียน `mockedBy` ลงใน screens.json ของ design

### P8 — คนขับ AI ทำ
**หลัก:** ผู้ใช้เรียกคำสั่งทีละตัว · `next` เสนอแต่ไม่รัน · หนึ่ง unit of work ต่อ session · ไม่มี orchestrator · ทุกคำตอบของผู้ใช้ถูกเขียนลงดิสก์ก่อน AI ตอบกลับ
**เหตุผล:** ระบบที่ AI ขับใช้ token มหาศาลและคนตรวจไม่ทัน · ความรู้ที่อยู่แต่ในบทสนทนาหายเมื่อปิด session · subagent ไม่มีทางถามผู้ใช้กลับ
**ในโค้ด:** ไม่มี script ใดเรียกคำสั่งอื่นเป็นลูกโซ่ · `ask` เขียนคำตอบก่อนแสดงรอบถัดไป · session ใหม่เริ่มด้วยการอ่านดิสก์ ไม่ใช่ถามว่าเมื่อวานคุยอะไร
**ถูก:** `next` พิมพ์ 3 ทางเลือกแล้วจบ · **ผิด:** `flow` ที่รัน req→design→mock ต่อกันอัตโนมัติ

## 3. Anti-patterns — เห็นเมื่อไหร่ให้หยุด

| อาการ | ทำไมอันตราย | ทำแทน |
|---|---|---|
| เอกสารกำกับยาวกว่าโค้ด · "ประตูที่เคาะแล้ว" เป็นร้อยแก้วหลายสิบข้อ | ทุกคำสั่งใหม่ต้อง consistent กับทั้งหมด → ซับซ้อนเรื่อย ๆ | gate ใน gates.json + function · ตัดสินใจบันทึกใน brain 1 บรรทัด |
| เขียนสเปก plugin ครบทุกข้อก่อนสร้าง | สเปก drift จากดิสก์ทันที ค่าบำรุงรักษาสูงกว่าค่าสร้าง | สเปก 1 หน้า → round 0 ที่รันได้ → ขยาย |
| ไฟล์เดียวเก็บทุกอย่างของ plugin | หลายพันบรรทัดใน 1 module | แตกตาม module/aggregate/app |
| AI เปิดทั้ง directory "เพื่อดูภาพรวม" | token รั่ว 200k+ ต่อหน้า | `core:query <id>` |
| AI เติมช่องว่างของสเปกเอง ("น่าจะต้องมี field นี้") | หนี้ที่ไม่มีใครรู้ว่ามี | GAP / Q ส่งขึ้นต้นน้ำ · Class B ห้ามเขียนโค้ด |
| คัดลอกข้อความกฎไปไว้อีกที่ | สองสำเนาไม่ตรงกันในสัปดาห์เดียว | อ้าง id · ไม่ copy |
| ตอบ "รับทราบ" ก่อนเขียนไฟล์ | ความรู้ตายพร้อม session | persist ก่อนตอบ เป็น DoD ของทุกคำสั่ง |
| ผ่าน gate โดยแก้สิ่งที่วัด (ลบ healthcheck แก้ assertion แก้ golden) | เขียวปลอม | P6 — ห้ามเสมอ · แดงที่พูดจริงดีกว่าเขียวที่โกหก |
| ทำ hotfix / product mode / migration ในเฟส 0–6 | ดึงแผนออกนอกลู่ | จองไว้เฟส 7 · จดใน backlog.md |

## 4. เมื่อสเปกไม่ครอบคลุม — ถามตัวเองตามลำดับ

1. **ใครเป็นเจ้าของ id นี้?** (`ids.mjs`) ถ้าไม่มี prefix → มันอาจไม่ใช่ artifact ใหม่ แต่เป็น field ของสิ่งที่มีอยู่
2. **script ไหนตรวจมัน?** ถ้าตอบไม่ได้ → เป็น LIMIT ไม่ใช่กฎ · อย่าเขียนลงคำสั่ง
3. **ผู้ใช้จะเห็นหรือทำอะไรที่ไม่มี artifact ประกาศไหม?** ใช่ → ต้นน้ำต้องรู้ก่อน (Q / GAP / CR)
4. **หลัง Cold Start ตอบได้จากดิสก์ไหม?** ไม่ → ยังไม่ได้ persist
5. **ไฟล์ที่จะเขียนเกิน 300 บรรทัดไหม?** ใช่ → แตกก่อนเขียน
6. **ต้องเป็นคำสั่งใหม่จริงไหม?** DoD เฟสปัจจุบันเขียวหรือยัง · plugin นี้มีครบ 6 หรือยัง · ส่วนใหญ่คำตอบคือ flag ของคำสั่งเดิม หรือ backlog
7. **ยังตัดสินไม่ได้** → หยุด ถามเจ้าของ บันทึกคำตอบลง brain 1 บรรทัด แล้วทำต่อ

## 5. "เสร็จ" แปลว่าอะไร

- **คำสั่ง** เสร็จเมื่อ: script รันได้ · เขียน artifact ลงดิสก์ · gate ของตัวเองมี function · fixture clean/dirty พิสูจน์ · คำสั่ง `.md` ≤40 บรรทัด
- **Plugin** เสร็จเมื่อ: `checks.mjs` export CHECKS+NEXT · `init` ลงทะเบียน root + gates · ≤6 คำสั่ง · SPEC.md ถูกลบ (คำสั่งและ checks คือสเปกแล้ว)
- **เฟส** เสร็จเมื่อ: DoD ใน `phase-plan.md` เขียวทุกข้อบน RentPoint · `gates.mjs` exit 0 · Cold Start question ตอบได้จาก `query`/`next` · เจ้าของบอก "เปิดเฟสถัดไป"

## 6. ศัพท์ของ specops

| คำ | ความหมาย |
|---|---|
| **gate** | ข้อจำกัดที่มี function ตรวจ · ERROR บล็อก · WARN รายงาน · **LIMIT** = ประกาศไว้แต่ยังไม่มี script ตรวจ พิมพ์ทุกครั้ง |
| **slice** | ผลของ `query`: record + up/down + CR ที่แตะ — สิ่งเดียวที่ AI อ่าน |
| **lane** | ทางเดินของ CR: `ui` (design UI/rbac → mock → dev revise → qa) หรือ `full` (กลับ req/design แล้วไล่ลงทั้งสาย) |
| **origin** ของ UI | `usecase` (ลูกค้าขอ) · `master` (จาก ENT reference) · `baseline` (ทุก app type ต้องมี) · `nfr` |
| **kind** ของ ENT | `aggregate` `entity` `reference` (ต้องมีหน้า master) `lookup` (ถามว่า master หรือ seed) `vo` (ไม่มีหน้า) |
| **enforces** | field บน step ของ UC ระบุว่า step นี้บังคับ BR เวอร์ชันไหน |
| **baseline** | รายการ UI/MCK + hash ที่ลูกค้าเซ็น = ขอบเขตของใบเสนอราคา |
| **vertical slice / TSK** | หน่วยงานของ dev: หนึ่ง capability ตัดครบทุกชั้น · CRUD = 1 |
| **Class A / B** | A = จัดเรียงสิ่งที่ design ประกาศแล้ว ทำได้ · B = affordance/field/route ใหม่ → GAP ห้ามเขียนโค้ด |
| **proof** | `{cmd, result, at}` ผลจริงจากการรัน — เงื่อนไขปิด TSK |
| **golden (GD)** | answer key ที่ได้จากการรันสคริปต์แล้วคนเซ็น · unit test ใช้คำต่อคำ |
| **callsheet** | `core:next` — บอกว่าทำอะไรได้ ไม่รันเอง |
| **Cold Start Test** | ปิดทุก session เปิดใหม่มีแค่ดิสก์ แล้วถาม · ตอบไม่ได้ = รั่ว |
| **persist-before-answer** | เขียนลงดิสก์ก่อนตอบผู้ใช้ทุกครั้ง |
