# backlog — things noticed during a phase that are not that phase's DoD

Constitution rule 9: nothing here is picked up before phase 6's DoD is green. One line each: where it was seen · what · the fix if known.

- **2026-09-05 · phase 5 dod · dev:task slice** — `sliceOf` picks entities by `invariants ∩ UC.enforces`, so UC-rental-001's slice omits ENT-001 Booking (invariants BR-004/005/009) and includes ENT-004 Payment (invariant BR-002). Better key: the aggregate whose STM the UC's steps move, plus the reference ENTs the steps select.
- **2026-09-05 · phase 5 dod · dev IMP file growth** — `dev/impl/TSK-001.json` is 232 lines for 17 IMPs; a slice with 22+ files crosses rule 4. Same fix as the tasks file: one file per record (`dev/impl/<TSK>/<IMP>.json`) or one line per IMP.
- **2026-09-05 · phase 5 dod · dev G-dev-005** — the orphan sweep only knows `.cs` for csharp; `.csproj`, `Dockerfile`, `docker-compose.yml` under a component root are never reported when no IMP owns them. Config files that matter to `run.up` should count.
- **2026-09-06 · phase 6 build · qa:cases http body** — a generated step sends the golden row's `input` as the request body verbatim, and `API.request` is checked for presence only, never used to name the fields. Where the two shapes differ (RentPoint: GD `{rate,pickup,return}` vs the endpoint's `{customerId,pickupDate,returnDate,equipmentIds}`) the call is wrong even after the path is fixed. Needs a mapping upstream — CALC input field → `API.request` field — or the step stays not runnable, which is the safe half of the behaviour it has today.
- **2026-09-06 · phase 6 dod · qa:finding source** — a DEF raised from `--evidence` with no failing run is written `source: "run"`, `run: null` (DEF-rental-003). One more value (`hand`) would say where the evidence came from without opening the file.
- **2026-09-06 · phase 6 dod · testproject §8 vs what phase 5 built** — §8's DEF-rental-001 needs the confirm step of UC-rental-002 (TSK-002, never built by the phase-5 DoD) and §8's DEF-rental-002 symptom (fee 3,000 → 1,000) cannot occur on code whose unit test asserts GD-rental-002 verbatim. Either the test project grows a TSK-002 with a deliberate BR-004 bug, or §8 / SPEC §Phase DoD are reworded to the gaps that exist (handoff gap → dev · missing boundary SCN → design, CR-004).
- **2026-09-06 · phase 6 build · design:scenario SCN without an AC** — 4 of 15 use-case scenarios name only the UC in `derivedFrom` (SCN-rental-008/009/011/014, all on UC-rental-005/006/007/009): a scenario that claims no acceptance criterion proves nothing anyone signed. Checked while making `qa:report` count AC coverage per AC — the four ACs it now reports (AC-rental-002/003/004/010) are genuine gaps, none of them belongs to those four scenarios' use cases. `design:usecase` writes AC per flow, `design:scenario` cuts one SCN per flow, so a flow with four ACs loses three.
- **2026-09-06 · phase 6 build · qa:cases cannot supply a path id** — a step is not runnable when `API.path` holds `{id}`, so every confirm/edit/delete endpoint stays out of reach even now that the resource segment is right: TC-rental-005/006 (`/api/bookings/{id}/confirm`) and eight more. `TC.data` already carries the golden row; it could carry the id a prior step created, or `run` could thread the previous step's response into the next one's path.
- **2026-09-06 · phase 6 build · qa:cases false pass on an exception flow** — a non-main flow expects `4xx`, and an endpoint answers 400 to a body it cannot parse, so TC-rental-004 (BR-rental-006@v1 maintenance) passed on `HTTP_STATUS=400` with an empty request and never exercised the rule. `expect` for an exception flow should name the status and the `title`/`rule` the refusal must carry, not any 4xx. Same root as the http-body line above.
- **2026-09-06 · phase 6 build · RentPoint api has no auth** — every `API` record says `auth: "required"` and nothing implements it; `POST /api/bookings/{id}/confirm` takes `by` from the request body, so the BR-rental-010@v1 audit records whatever the caller types, and any caller can confirm any booking. TSK-001 set the pattern (`by: customer:{req.CustomerId}`) and TSK-002 followed it. Auth belongs to a TSK of its own, from ACL-014/ACL-035/ACL-047 and `project.json.apps[].auth`; until then the slice is a fixture, not a system.
- **2026-09-06 · phase 6 build · design:scenario cuts one SCN per flow** — four acceptance criteria on the rental module have no scenario at all (AC-rental-002/003/004/010), now visible because `qa:report` counts per AC. AC-rental-004 is the boundary CR-004 was opened about, so CR-004 cannot be satisfied until `design:scenario` cuts one SCN per AC rather than one per flow.
- **2026-09-06 · phase 6 dod · one dev DEF per case collides with what `cases` auto-raises** — `cases` writes a dev-routed DEF for every unrunnable case under a verified use case, and `finding` refuses a second dev DEF on the same case. On a fresh state the handoff-gap DEF lands first and the real symptom (§8 DEF-rental-001 on TC-rental-006) can never be recorded; on RentPoint it worked only because DEF-rental-004 was raised before `--refresh`. Either `cases` raises its gap DEF with a `kind: handoff` that `finding` may supersede, or the rule becomes one DEF per case per routing per cause.
- **2026-09-06 · phase 6 dod · a `cases`-raised DEF never retires when its gap is fixed upstream** — DEF-rental-001/002 (run 1, `/api//{id}`) stay open although both cases now run: a DEF closes only when its case passes, and TC-rental-003 fails on the body shape while TC-rental-004 is `partial`. `cases --refresh` sees the gap is gone and could write `retired` with the reason, leaving `verified` to a green run.
